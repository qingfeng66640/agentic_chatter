# 分句行为说明

分段发送会把模型产出的一整段回复拆成若干条消息陆续发出。拆分的切点选择
直接影响观感：切在语义边界上就像真人打字，切在词中间就像卡顿或乱码。

本文说明 0.8.0 起分句如何处理**不可拆单元**。

## 为什么需要单元概念

早期实现按字符位置从后往前找标点，找不到就按固定长度硬切。它完全不知道
表情和颜文字的边界，于是出现两类损坏：

**硬切损坏**。切点落在单元内部时直接断开：

| 单元 | 被切开的样子 |
| --- | --- |
| `(´･ω･\`)` | `(´･ω` + `･\`)` |
| 👨‍👩‍👧 | 👨 + 👩‍👧（渲染成两个不同表情） |
| 👋🏽 | 👋 + 🏽（肤色修饰变成孤立方块） |

**标点损坏**。即使没有触发硬切，颜文字内部的标点也会被当成语义边界：

| 单元 | 命中的切分规则 |
| --- | --- |
| `(´;ω;\`)` | `;` 属于软标点 |
| `(，´ω´，)` | `，` 属于软标点 |
| `(。´ω´)` | `。` 属于句末标点 |
| `(；ω；)`、`(！ω！)` | 同理 |

默认配置 `[humanize].max_segment_chars = 60`，因此只要回复超过 60 字且单元
落在切点附近就会触发。在覆盖常见写法的测试集上，130 个可能的切点全部会
破坏单元。

## 现在的切分规则

切分前先扫描全文，识别出**不可拆单元**，再把它们压缩成单个原子参与切分。
切分只在原子边界上进行，单元内部的标点对切分器不可见。

三步：

1. **识别单元**。表情序列按完整 grapheme cluster 整体识别，覆盖肤色修饰
   （`U+1F3FB`–`U+1F3FF`）、ZWJ 组合、变体选择符（`U+FE0E`/`U+FE0F`）、
   keycap（`1️⃣`）与 tag 序列（旗帜）。颜文字按结构识别，覆盖成对括号
   （`()[]{}<>（）［］｛｝【】〔〕〖〗`，含 `(<(=･ω･=)>)` 这类嵌套）、
   波浪号包裹（`~ 〜 ～`，含 `〜(´ω｀〜)` 这类波浪号落在括号内的写法）、
   尾巴外挂（`(๑•̀ㅂ•́)و✧`）、中点对称的裸颜文字（`、´ω´、`）
   以及网络缩写（`QAQ`、`orz`、`2333`、`TAT` 等）。

2. **原子化切分**。每个单元作为单个原子参与标点查找与硬切，原子内部不可再分。

3. **边界回退**。找不到标点时退到不超过上限的最后一个原子边界，而不是按
   字符下标硬切。

### 哪些不算颜文字

括号里的普通文字不会被误判：

```text
(注)    (abc)    (123)    [1]    <div>    {key}
（重要）  （括号）  (hello world)  (1+2)*3  a<b>c
```

判据是括号内是否含「五官」构件——嘴型修饰符、几何眼形、泰文眼珠、希腊
字母等；仅有两个中点时也按裸颜文字处理。仅含普通文字或数学符号的括号
内容不构成单元。

## 超长单元

单个单元本身超过 `max_segment_chars` 时**不会**被拆开，而是作为整体送出。
消息长度会略微超出上限，这是有意的取舍：

- 超长消息只是不够好看，平台不会因此丢内容。
- 拆散颜文字是内容损坏，用户会看到乱码。

例如下面这条在 `max_segment_chars = 10` 时会原样发出一条超限消息：

```text
甲甲甲甲甲甲甲甲甲甲(((((*´ω`*) ))))乙乙乙乙乙乙乙乙乙乙
```

## 完整性自检

每次分段完成后会校验两条不变量，违反即抛出 `AssertionError`：

1. 所有分段拼接后与清洗后的原文完全一致（不丢字、不改内容）。
2. 每个不可拆单元必须完整落在某一段内。

这样即使将来有人改动切分逻辑导致回归，也不会静默发出损坏的消息。

## 关于 regex 依赖

表情簇识别使用 `regex` 包的 `\X`（完整 grapheme cluster）与 Unicode 属性。

插件在 `manifest.json` 中声明该依赖，核心会在插件加载前自动检测并安装：

```json
"python_dependencies": ["regex>=2024.0.0"],
"dependencies_required": false
```

`dependencies_required` 为 `false`，因为 `regex` 只影响识别精度，缺失时功能不会中断：
自动降级为手写状态机，ZWJ 组合、肤色修饰与变体选择符仍能正确保持，仅
Unicode 边界情况（如印度语系连写）不如 `\X` 完整。因此依赖装不上时插件仍照常加载。

## 相关配置

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `[humanize].max_segment_chars` | 60 | 单条消息的目标最大字符数 |
| `[humanize].max_segments` | 4 | 单轮最多切分成几条 |
| `[humanize].typing_cps` | 8.0 | 模拟打字速度（字符/秒） |
| `[humanize].max_typing_delay` | 4.0 | 单条消息的最大延迟秒数 |

默认值以 `config.py` 为准。调整 `max_segment_chars` 不会影响单元完整性：
无论上限设得多小，单元都不会被拆开。

## 排查

**颜文字仍被拆开。** 先确认该写法是否被识别为单元：

```python
from agentic_chatter.humanize.grapheme import find_units

print(find_units("你的文本 (´･ω･`)"))
```

返回空列表说明该写法尚未纳入识别规则。若单元已被识别但仍被拆开，
说明 `_split_once` 的原子边界回退被改动——此时完整性自检应当抛出
`AssertionError`，可据此定位。
