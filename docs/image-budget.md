# 图片预算计量与归因

适用版本：`[Unreleased]`（`max_input_images` / `max_input_image_bytes`）

原生多模态（`[plugin].native_multimodal`）开启后，主 Agent 的 ACT 阶段会把消息里的图片
内联进请求。本文档说明**体积怎么算**、**超限时怎么归因**，以及**日志字段怎么读**。

---

## 1. 计量口径：原始图片字节

`max_input_image_bytes` 与单张硬上限 `MAX_SINGLE_IMAGE_BYTES`（12MB）都按
**原始图片字节**计量，即图片解码后的二进制大小，**不是** base64 文本长度。

```python
raw = len(body) * 3 // 4 - padding   # body 为剥掉前缀与空白后的 base64 主体
```

`padding` 是末尾 `=` 的个数。base64 每 4 个字符编码 3 字节，但 `=` 是补位符不携带数据，
因此不能只用 `len(body) * 3 // 4`——那会把 3,500,000 字节的图算成 3,500,001。

### 为什么口径必须是原始字节

base64 会把二进制膨胀到 4/3 倍。若按 base64 长度计量：

| 场景 | 原始体积 | base64 长度 | 后果 |
| --- | --- | --- | --- |
| 手机随手拍 | 3.5 MB | 4.67 MB | 默认 8MB 预算只装得下 1 张 |
| 单张上限 | 9 MB | 12 MB | 等效原始上限被压到 **9 MiB** |
| 单张上限 | 10 MiB | 13.33 MB | 被丢弃，尽管远未超过配置宣称的 12MB |

具体影响：

- **累计预算**：默认 8MB 装不下 2 张 3.5MB 的手机照（base64 口径 9.33MB），
  发 3 张会被静默丢掉 2 张——而 `max_images=3` 一张都没触顶。
- **单张上限**：12MB 上限在旧口径下只等价 9 MiB 原始图片。原始体积**达到**
  9 MiB 时 base64 化恰好等于 12 MiB，再多一个字节就被丢弃。

> 历史上曾用 `len(data)` 作为闸门口径（主仓 `docs/guides/agentic-chatter-multimodal-image-budget.md`
> 记录了该决策，理由是"避免为发 3 张而全量解码 16.5 MiB"）。该决策已被本次口径变更取代：
> `len(body) * 3 // 4 - padding` 同样是纯字符串运算，无需解码。

## 2. 两层预算

| 上限 | 常量 / 配置项 | 默认 | 豁免 |
| --- | --- | --- | --- |
| 单张硬上限 | `MAX_SINGLE_IMAGE_BYTES` | 12 MiB | 无，**首张同样受限** |
| 单次累计预算 | `[plugin].max_input_image_bytes` | 8 MiB | **首张豁免累计预算** |

- 单张超限：直接丢弃该候选，继续往后选。
- 累计超限：跳过该候选，继续往后填额度。
- `max_input_image_bytes = 0` 表示不按体积限制。

首张豁免累计预算，是为了避免预算偏小时模型完全看不到图。它不影响单张硬上限，
也不受张数上限影响。

实际总量上界：

```
min(max_input_images × 12MiB, (max_input_image_bytes > 0 ? max_input_image_bytes : ∞) + 12MiB)
```

### 选取顺序

按「本轮优先、统一新→旧」：

1. 正文被 `[图片(<image_id>)]` **显式引用**的图优先；
2. 未被引用的图仅在还有**裸占位符** `[图片]` 可认领时才计入预算。

正文里没有位置的图不会白白吃掉名额——否则真正要发的图会被挤掉。

## 3. 丢弃原因码

告警日志的 `原因=` 字段取值：

| 原因 | 含义 | 常见触发 |
| --- | --- | --- |
| `count` | 张数上限截断 | 候选多于 `max_input_images`，且确有图因张数被丢 |
| `bytes` | 累计体积超限 | 装满 `max_input_image_bytes` 后装不下后续候选 |
| `oversize` | 单张体积超限 | 某张图原始体积超过 12 MiB |
| `unusable` | 图片载荷不可用 | 缺 `image_id`，或历史图 `data` 回填失败 |
| `invalid_payload` | 载荷非法 | 媒体项有 `data` 但不是合法 base64 |
| `placeholder_slots` | 正文占位符位置不足 | 正文只有 1 个 `[图片]`，却有 3 张可用图 |
| `both` | 张数与体积双超 | 两类上限**各拒了至少一张**（约束的是不同候选） |
| `unknown` | **无法归因** | 有图被省略，但没有任何预算证据支撑 |

> ⚠️ 历史版本的 `trimmed` 判据只比较"内联数 < 去重数"，不区分真实死因，
> 于是**字节预算触发时也报 `count`**——3 张图只进 1 张，日志写"张数超限"，
> 而张数上限根本没触及，排查方向被直接带偏。现改为按证据归因：
> `count` 要求 `dropped["count"] > 0`（确有图因张数上限被丢弃）。

### `count` 与 `bytes` 不互斥

两个桶约束的是**不同候选**，可以同时为正。一次遍历中：大图因累计体积被跳过后，
后续小图把剩余张数名额占满，再后面的候选就因张数满被丢——此时
`count > 0` 且 `bytes > 0`，`reason=both`。

`both` 要求**两类证据同时存在**，而不是"体积超标 + 任意省略"。

> 历史版本用"体积超标 + 任意省略"就报双超，于是一行日志里同时出现
> `丢弃(张数)=0` 与 `原因=张数与体积双超`，把排查方向引向"调大
> `max_input_images`"这一对该场景完全无效的动作。

### 为什么会出现 `unknown`

只有同时满足以下条件才会归因为 `unknown`：正文里有图被省略成 `[图片已省略]`，
但没有任何预算证据。若日志出现 `unknown`，说明省略发生在预算之外，
应检查载荷本身是否合法（见第 5 节）。

## 4. 日志字段

预算告警形如：

```
[xxxxxxxx] 多模态图片预算生效 事件=多模态图片超限
引用=21 去重=16 实际内联=3 上限=3 原始体积=...,B 体积上限=...,B
丢弃(张数)=13 丢弃(体积)=0 丢弃(单张超限)=0 缺ID=0 缺载荷=0 原因=张数超限
```

| 字段 | 含义 |
| --- | --- |
| `引用` | 消息中带可用载荷的图片媒体项总数（未去重） |
| `去重` | 按 `image_id` 去重后的不同图片数 |
| `实际内联` | 真正进入请求体的图片数 |
| `原始体积` | 内联图片的**原始字节**总和 |
| `丢弃(张数)` | 因张数上限被丢的张数 |
| `丢弃(体积)` | 因累计预算被丢的张数 |
| `丢弃(单张超限)` | 因单张硬上限被丢的张数 |
| `无位置` | 正文占位符位置不足而无处安放的候选数 |
| `缺ID` | 媒体项缺 `image_id` 的个数（见第 5 节） |
| `缺载荷` | 媒体项有 `image_id` 但缺 `data` 的个数 |
| `载荷非法` | 发射阶段被拒绝的载荷个数（有 `data` 但不是合法 base64） |

## 5. 静默路径：`缺ID`、`缺载荷` 与 `载荷非法`

历史上这三类图片被省略时**完全没有预算侧日志**：正文里已经写了 `[图片已省略]`，
但因为它们进不了预算候选，或在发射阶段才被拒，四个丢弃桶全为 0。

| 现象 | 成因 | 后果 |
| --- | --- | --- |
| `缺ID > 0` | 媒体项没有 `image_id` | 无法与正文占位符关联，永不内联 |
| `缺载荷 > 0` | 有 `image_id` 但 `data` 为空 | 历史消息入库时剔除了 base64，磁盘回填失败（文件已被清理） |
| `载荷非法 > 0` | 有 `data` 但不是合法 base64 | 发射阶段被 `_safe_image` 拒绝 |

`缺载荷` 的常见触发是媒体文件被清理：历史消息入库时按 `image_id` 剔除 base64
（避免数据库膨胀），读取时按哈希回查文件，文件已删则回填失败。

`载荷非法` 通常来自上游写入的损坏载荷，或形似文件路径的字符串——`Image`
遇到无法解码的字符串不会抛错，而是当**路径**读盘并 base64 编码塞进请求体，
故必须显式拦截。

> `载荷非法` 只在载荷**进入发射阶段**时才计数。若名额已满（`max_images`
> 用尽），非法载荷会在选择阶段就被挤掉，`_safe_image` 不会被调用，
> 此时 `原因=张数超限` 同样是正确的。

## 6. 排查路径

**图片被省略，先看 `原因=`：**

| 原因 | 检查 |
| --- | --- |
| `张数超限` | 候选是否多于 `max_input_images`？需要更多图就调高该值 |
| `累计体积超限` | 调高 `max_input_image_bytes`，或减少单轮图片 |
| `单张体积超限` | 确认该图原始体积是否真的超过 12 MiB |
| `正文占位符位置不足` | 正文里的 `[图片]` 少于可用图片数，需检查占位符生成 |
| `图片载荷不可用` | 看 `缺ID` / `缺载荷` 计数，见第 5 节 |
| `图片载荷非法（非 base64）` | 看 `载荷非法` 计数，见第 5 节 |
| `原因不明` | 预算都没触及，检查占位符与 `image_id` 是否匹配 |

**验证配置是否如预期生效：**

配置里写 `max_input_image_bytes = 8388608`（8 MiB），指的是**原始图片总体积 8 MiB**。
若按 base64 口径理解，8 MiB 实际只装得下约 6 MiB 的原始图片，会比预期少发一张。

**日志里 `原始体积` 略大于 `体积上限` 是正常的**——首张豁免累计预算。
只有当确有图被省略时才会判体积超限并告警，不会因首张豁免产生误报。
