# agentic_chatter v0.8.0 升级说明

本文面向从 0.7.x 升级到 0.8.0 的使用者。0.8.0 有两处会**改变运行时行为**的变更，
以及一项会**直接挡住加载**的兼容性要求提升。

完整变更清单见 [CHANGELOG.md](../CHANGELOG.md) 的 `[0.8.0]` 段。

> 本页记录 0.8.0 的历史升级要求。**从 0.8.2 起，最低核心版本为
> `1.3.0-alpha.2`**；安装当前版本前请先升级核心。
> 较早的 alpha.1 核心可能错误过滤限定群聊或私聊的外部组件，
> 因此不能继续按本页历史表格中的 alpha.1 下限判断当前版本兼容性。

## 一、最低核心版本提升（会阻止加载）

| 项 | 0.7.x | 0.8.0 |
| --- | --- | --- |
| `min_core_version` | `1.2.0-alpha` | `1.3.0-alpha.1` |

加载器按 PEP 440 做 `>=` 比较（`src/core/components/loader.py`），核心版本低于
`1.3.0-alpha.1` 时插件**拒绝注册**，而非降级告警。升级前请确认宿主核心版本：

```bash
# 核心运行时版本以此处为准
grep CORE_VERSION src/core/config/core_config.py
```

注意 `pyproject.toml` 的 `version` 字段是**打包版本**，不参与此比较。

## 二、原生图片预算：行为变更

### `max_input_images` 语义改变

这是本次最需要注意的一处。旧行为与配置项字面含义不符，0.8.0 将其修正：

| | 0.7.x | 0.8.0 |
| --- | --- | --- |
| 约束对象 | **仅本轮新输入**的图片 | **单次请求的全部**图片 |
| 历史图片 | 完全不受限 | 与本轮新图共享同一预算 |

旧实现中历史图片经 `set(index).difference(preferred_ids)` 全量放行，长对话下请求体
随历史线性膨胀。生产实测单请求内联 21 张图、base64 达 16.57 MiB，被上游网关以
`upstream error: do request failed` 连续拒收四次。

**如果你的配置文件里显式写了 `max_input_images`**，升级后实际传入的图片数量会
明显少于升级前——这是修复本身的目的，不是回归。未显式配置者使用新默认值 `3`。

### 选取顺序

预算内按以下顺序取图，同一张图只内联一次：

1. 正文里被**显式引用**的图优先（`[图片(<image_id>)]` 占位符点名到的）；
2. 本轮新消息的图（`[图片]` 裸占位符认领）倒序在前；
3. 历史消息的图倒序在后。

即「本轮优先、统一新→旧」。裸占位符没有 `image_id`，只能按位置近似认领，属于
已知的有界降级。

## 三、新增 `max_input_image_bytes`

```toml
[plugin]
max_input_images = 3          # 张数上限，默认 3，取值 0-32
max_input_image_bytes = 8388608  # 体积上限（字节），默认 8MB，0 = 不按体积限制
```

选取时**跳过**装不下的图继续往后试，而不是遇到第一张超预算就停，因此实际发出
的总量可能低于上限值。

### 单次请求图片体积的实际上界

```
min(max_input_images × 12MB, (max_input_image_bytes > 0 ? max_input_image_bytes : ∞) + 12MB)
```

其中的 `+ 12MB` 来自**首张图片豁免累计预算**：即使体积上限配得很小，至少仍会
发出第一张，避免模型完全看不到图。但 12MB 单张硬上限对首张同样生效。

据此选值：

| 期望 | 建议配置 |
| --- | --- |
| 与默认一致（3 张 / 8MB） | 保持默认 |
| 视觉模型上下文窗口较小 | 调小 `max_input_image_bytes`，如 4MB |
| 明确知道上游能吃大请求 | 调大，但同时确认网关侧限制 |

## 四、模型实际看到的占位符形态

预算不足时不会静默丢图，正文里会留下明确标记：

| 情况 | 正文中的呈现 |
| --- | --- |
| 因预算被舍弃 | `[图片已省略]` |
| 同一张图再次出现 | `[图片(同图,上文已提供):描述]`（保留描述） |
| 上游产出的无 `image_id` 形态 | `[图片已省略]` |

如果模型反馈"看不到图片"，先确认它看到的是哪一种标记，再对照下面的日志判断
是预算问题还是上游问题。

## 五、日志字段变化

预算收紧时会记录 `事件=多模态图片超限`：

```
[pid] 多模态图片预算生效 事件=多模态图片超限 引用=21 去重=16 实际内联=3 \
      上限=3 体积=1804728B 体积上限=8388608B 原因=张数超限
```

| 字段 | 含义 |
| --- | --- |
| `引用` | 正文中出现的图片占位符总数（含重复引用） |
| `去重` | 按 `image_id` 去重后的不同图片数 |
| `实际内联` | 真正进入请求体的图片数 |
| `体积` | 实际内联图片的 base64 总字节 |
| `体积上限` | `max_input_image_bytes` 的实际取值 |
| `原因` | 触顶的是张数、体积，还是两者都有 |

另有 `事件=多模态图片载荷非法`：图片载荷非法（不是合法 base64）时记录，
该图按 `[图片已省略]` 降级，**不会**再让整个 ACT 回合崩溃。

排查建议：`引用` 与 `去重` 差距大说明同一张图被反复提及；`实际内联` 远小于
`去重` 时调大预算；`原因` 为「体积超限」说明该调体积而非张数。

## 六、DECIDE 阶段默认值重配

0.8.0 同时重配了 18 项 DECIDE 默认值，**会改变机器人的开口倾向**。详见
CHANGELOG `[0.8.0]` 的完整数值表。影响最大的是本地直通边界：

| 配置项 | 0.7.x | 0.8.0 |
| --- | --- | --- |
| `local_reply_lower_bound` | 0.30 | 0.35 |
| `local_silent_upper_bound` | -0.25 | 0.2 |

两者共同作用，**灰区从 `(-0.25, 0.30)` 收窄为 `(0.2, 0.35)`**，交给
`sub_actor` / Jev 裁决的消息显著减少。若你依赖 Jev 的灰区判断，需要重新评估
`min_confidence` 等阈值。

其余 16 项为上下文预算放宽与评分权重重配，同样记录在 CHANGELOG。

## 七、升级步骤

1. 确认宿主核心版本 ≥ `1.3.0-alpha.1`，否则插件不会加载。
2. 备份现有配置文件，重点关注 `[plugin].native_multimodal`、
   `max_input_images`、`[decision]` 整节。
3. 检查配置中是否显式写过 `max_input_images`——若有，评估新语义下的取值。
4. 若此前只调过 `max_input_images` 而没调 `max_input_image_bytes`，新体积闸门
   会用默认值 8MB 生效。若你的上游模型对图片体积敏感，建议显式配置。
5. 观察升级后首个多图会话的 `multimodal_image_limit` 日志，确认实际内联数量
   符合预期。
6. 观察数日灰区裁决的触发频次是否符合预期（本次调优后应显著下降）。
